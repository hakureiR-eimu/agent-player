This article is [timeless](https://vic3.paradoxwikis.com/Category:Timeless) and should be accurate for any version of the game.

**Scripting** is how mod-makers are able to add, change, and interact with content in Victoria 3. This is done using Paradox's custom scripting language. This language has no official name, but is referred to as "Paradox Scripting Language", or "**PDXscript**" for short, by the community. In principle, it is designed to be easy to read, learn, and debug. In Victoria 3, the majority of functions are designed to be human-readable, such as `set_variable` or `add_modifier`.

**PDXscript** is used in content contained in the `/common` and `/events` folder. This includes content such as events, country/flag definitions, modifiers, cultures, goods, and so on.

*Note*: *this guide does not cover the following topics-*

- Most of the mechanics surrounding assimilation, trade, military formation movement/battles, wages, and so on. These are done in "game code" and are not exposed to mod-makers. We call these mechanics "hard-coded." This is usually done for performance reasons since script is *always* slower than code
- The GUI Scripting Language, used by files in the `/gui` folder, is a separate scripting language. PDXscript is unable to directly access the UI or UI functions. [Scripted GUIs](Scripted gui.md) can be used in cases where we want to execute script via a UI element.
- [History](History modding.md) files in `/common/history`. These use a static script system, but are able to use script effects during execution.
- [State Region](Map modding.md) files located within `/map_data/state_regions`. These use a unique static script that is read *once during game startup.*
- The game's [Localization](Localization.md), within `/localization`. These files use strings that are able to call UI functions. These can be called in script, such as in scripted button localization or script value breakdowns. There are also some cases where localization functions will check script-side elements, such as in `/common/customizable_localization` or `/common/trigger_localization`.

*Note: Some developers will occasionally refer to script as "Jomini script." This is because it is a part of the larger Jomini shared library. "Clausewitz" is the name of the game engine.*

## Overview

This is meant to be a quick guide to learning and using PDXscript in Victoria 3.

This guide should give you a solid footing to start modding, but isn't a substitute for practicing modding yourself. It is generally good practice to find examples of your desired script either in the base game or other mods or to search files for use cases of a given effect or trigger if you are curious about usage or implementation. You can also reach out to the modding community via the [Victoria 3 Mod Co-op](https://discord.gg/pJCJ8H7HB7).

### Documentation

Victoria 3 has its own built-in script documentation. This can be generated by executing the console command `script_docs` at runtime.

This will generate the documentation files at `~\Paradox Interactive\Victoria 3\docs`.

These files will list the following important information:

- **Effects** - These are used to change the game state in some way.
- **Triggers** - These are used to check a given aspect of the game state.
- **Event Targets** - These are used to change scope mid-script execution.

The script docs also include information about the following:

- **Custom Localizations** - This is a list of compiled custom locs. These are called in localization to change the displayed text based on script-defined triggers.
- **Modifiers** - This is a list of all available [modifier types](Modifier types.md). These are used to build the [Static Modifiers](Modifier modding.md) used in-game.
- **on_actions** - This is a list of all available [on actions](On action.md). These are used to execute [Events](Event modding.md) or [Effects](Effect.md) whenever specific actions occur during gameplay.

**Limitations:**

PDXscript is an incredibly powerful and flexible tool to reshape the game. However, it has the following limitations:

- No direct access to the UI or any UI-specific values
- Cannot access the operating system or user input
- No string manipulation
- Significantly slower than functions executed "in code"

### Debugging

- Issues with script will normally print an error to the logs. These are located at `~\Paradox Interactive\Victoria 3\logs`. This should be your first stop when attempting to resolve why your script doesn't work.
  - *Warning*: If you encounter a CTD (crash-to-desktop), the error that crashed the game will usually not print to the error log. This means that the last error in in the log is not consistently the error that actually caused the crash.
- Launching Victoria 3 with the `-debug_mode` flag launch option will enable both [console commands](Console commands.md) and file hotloading
  - The **Object Explorer** can be used to test script using the script runner
- amtep's [Tiger Validator](https://github.com/amtep/tiger) provides in-depth script validation for Victoria 3

### Terminology

Victoria 3 has an extensive jargon to informally refer to scripting features, many of these are shared with other Paradox modding communities:

- **Script:** This is the 'code' that modders can use to change how the game functions.
- **Effect:** Script that executes a change on the gamestate
- **Trigger:** Script that checks the gamestate; mostly used to condition effects/events
- **Scope:** The context for a trigger or effect; also used to signifying changing context to an object, i.e. "Scoping a country"
- **Scope Link / Event Target:** A keyword for a scope or game value
- **Type:** The 'class' for a game object
- **Key:** The script name of a type
- **Tag/TAG:** The key for a country, such as `FRA` for the country France
- **Logs**: The game logs printed to `~/Paradox Interactive/Victoria 3/logs`; these often contain information regarding errors or script collisions
- **Docs:** The in-game documentation supplied by the development team. These are most often found in the directory of the relevant script. The generated **script docs** are also included in this term.
- **CTD:** Short for "crash to desktop;" an error that causes the game to unexpectedly close

## Basics

This guide assumes you have already set up your mod folder and are working on creating/modifying content. See

for initial mod setup.

### Syntax & formatting

##### Script structure

PDXscript uses statements that are structured as:

`<lvalue> <operator> <rvalue>`

These are referred to as "left value," "operator," and "right value" by the game and are referenced as such in the documentation and logs. All scripting operations *require* a valid "left value" and "right value" linked by an operator.

In general, any statement will be structured roughly like one of the following:

- `x = y` – a "simple" statement
- `x = { y = z }` – a "complex" or "block" statement

Examples:

- `is_subject = yes`
- `add_treasury = 100`
- `debug_log = "hello world"`
- `overlord = { add_modifier = modifier_regency }`

##### Blocks & indenting

While simple script triggers and effects often take the form of `x = y`, more complex scripting or any parameters require the use of curly brackets (`{}`). This is referred to as a **block.**

Indentation style, and whitespace generally, has no effect on the execution of the script itself. However, **indentation is critically important for readability and debugging**.

Generally, every code block should be indented in a way that makes it clear how effects, triggers, and scopes are related. Paradox appears to use a style similar to the *Kernighan & Ritchie (K&R) style* in their script, and this has been widely adopted by the modding community.

```
c:GBR = {
    add_treasury = 50000
}
```

Every code block opens with an lvalue and an operator. The contents within the curly brackets function as its rvalue. Every statement within these brackets must themselves follow the `<lvalue> <operator> <rvalue>` structure.

**Note:** *Certain blocks are "list blocks" and do not follow this convention. These are noted on their respective wiki pages.*

###### Script comments

The # symbol will turn everything after it in the same line into a "comment." This means that it will be ignored by the engine when compiling your script. You can use this to leave notes for yourself or others regarding your script. There are no multi-line comments, so each comment line must start with #.

### Scopes & targets

##### Scopes

See the
Scope
page for more information regarding scopes.
Scopes are the game objects used to evaluate triggers and execute effects. Triggers and effects have specific scopes they function in. Scopes can be a country, a state, a pop, a building, and so on. Global triggers and effects can be used in any scope.

Scripted content usually has a base scope depending on where its execution originated from. This is called the **root** scope. For most scripted content, this scope is the country receiving the content. Script is able to change scope by using **event targets**, such as changing scope from a *building* to its *owner*.

##### Changing scope

See
Event targets
for more information regarding event targets.
**Event targets** (also called *Scope Links*) allow us to switch from one scope to another (called "scoping" by the community). For example:

```
# This starts in the country scope
ruler = { # Now we have changed to the character scope for the country's ruler
  interest_group = { # Finally, we change to the interest group that the ruler is a member of.
    add_modifier = modifier_failed_coup
  }
}
```

Certain event targets also **require data** to function. For example:

```
# This is the country event target. In this case, the target scopes to a country with the GBR definition.
c:GBR = {}

# This is the state region target. In this case, the target scopes to the STATE_ATTICA state region.
s:STATE_ATTICA = {}

# This is the market goods target. In this case, the target scopes to the meat good within a market scope.
market = {
  mg:meat = {}
}
```

Certain event targets are **global links**. This means that they can be invoked from any scope. For example:

```
# This will always scope to a country with the definition "FRA"
c:FRA

# This will always scope to the "catholic" religion
rel:catholic

# This will always scope to the "liberal" ideology
ideology:ideology_liberal
```

*Available event targets are shown in docs/event_targets.log . This includes information about supported input and output scopes.*

##### Chaining scopes

Scopes can be chained using **dot linkage** like this: `a.b.c`

For example, this script:

```
ruler.interest_group.ig_clout = {}
```

Is identical to:

```
ruler = {
  interest_group = {
    ig_clout = {}
  }
}
```

### Special targets

`root` - The *origin scope* of a particular script instance. This changes depending on where the script was executed from. While this is often the country scope, this is neither a convention nor consistent.

`prev` - The *previous scope* in your scope chain. This can be used to access an object available from within a specific scope and quickly return to your original scope. The `prev` target can be chained to "walk backwards" through a scope chain, i.e. `prev.prev = {}`

`this` - The *current scope*. This is used to compare the identity of an object once you've scoped to it. This is commonly used with **iterators** or in situations where you are not sure if the scoped object is the one you want (for example, a journal entry being gated to a single country).

### Operators

##### Comparison operators

*Scopes* are compared using = or !=. For example:

- `ruler != ig:ig_devout.leader`
- `infamy = 100`

Values can be compared with <, <=, >, >=, =, and !=. For example:

- `ruler.popularity > 50`
- `ig:ig_landowners.ig_clout <= 0.25`
- `c:RUS != this`
- `root.gdp > c:FRA.army_size` (this is a nonsense comparison, but it goes to show that you can compare *any* two values

*!= means "does not equal" and can be used for both scopes and values.*

##### Boolean operators

PDXscript supports the following boolean operators:

`AND, OR, NOT, NOR, NAND`

These are used within trigger blocks to evaluate the game state. For example:

```
# This will return true if the country has a treasury over 50000 or is not at war.
OR = {
  treasury > 50000
  is_at_war = no
}
```

- **AND** returns true if **all** contained conditions are **true**.
- **OR** return true if **any** contained condition is **true**.
- **NOT** and **NOR** are actually the same. They return true if **all** contained conditions are **false**.
- **NAND** returns true if **any** contained condition is **false**.

Trigger blocks are always use **AND** as the implicit base operator.

##### Assertion operator

?= is the safe assertion operator. This checks that the `lvalue` object exists before attempting a comparison or scoping to it for script execution as specified in the `rvalue`.

For example, this script:

`capital ?= state_region.s:STATE_HOME_COUNTIES`

Is functionally identical to this script:

```
exists = capital
capital = state_region.s:STATE_HOME_COUNTIES
```

This helps avoid errors from unset/null scopes and makes your script more compact. However, if you *need* the error printed in the event of a null scope, you should allow the error to be printed by using =.

A key feature of PDXscript is its ad hoc implementation for each file type. The files in each sub-directory of `/common` will often present you with **list blocks**, **script math blocks**, or other trigger blocks that are specific to that file.

		state_building_barrack_max_level_add = 25
		state_building_conscription_center_max_level_add = 25

## Triggers

See
Triggers
for documentation of triggers.
Triggers are used to build condition statements by reading the game state, such as the ideology of a character, the ownership of a state, and much else.

Triggers can only be used within *trigger blocks*. They each have a predetermined syntax and are usually evaluated by the game engine in the current scope. Some triggers can be used in any scope, while others evaluate a different object relative to the current scope.

*Note:* A trigger block will only return true when all of its triggers are also true. This behavior can be modified with boolean operators.

Triggers come in two basic types, *inline* and *block:*

**Inline triggers** take a simple target, such as a scope, script value, or defined type:

```
# root = country
capital.state_region = s:STATE_MONTENEGRO

# root = character
interest_group.leader.ideology = ideology:ideology_moderate
```

**Block triggers** are more complex and often take multiple targets, such as a scope and script value.

```
# root = country
radical_fraction = {
    culture = cu:han
    value >= 0.10
}

calc_true_if = {
	 amount >= 2
	 has_law_or_variant = law_type:law_autocracy
	 has_law_or_variant = law_type:law_oligarchy
	 has_law_or_variant = law_type:law_landed_voting
	 has_law = law_type:law_monarchy
	 has_law_or_variant = law_type:law_theocracy
}
```

**Early Out / Return Early:**

Unless they are invoked in a tooltip, trigger blocks usually follow the "early-out" principle.

As mentioned above, trigger blocks only return true when all of their triggers are true. "Early out" means that as soon as a trigger in a block evaluates to false, no further triggers in that block are evaluated. This feature is essential for avoiding errors and creating performant script.

```
# For example, this script will print errors should FRA not exist:
c:FRA.country_rank >= rank_value:great_power

# This can be avoided by two methods; the first is using the exists trigger:
exists = c:FRA # If FRA does not exist, the trigger fails here, and will not advance to the second trigger
c:FRA.country_rank >= rank_value:great_power

# The second method uses safe assertion:
c:FRA ?= { # If FRA does not exist, the trigger will fail before evaluating anything within the block
    country_rank >= rank_value:great_power
}
```

## Effects

See
Effects
for documentation of effects.
Effects change the current game state, such as by such as creating or killing a character, changing the ownership of a state, and much else.

Effects can only be used in *effect blocks*. They have a predetermined syntax and are usually executed by the game engine in the current scope. Some effects can be used in any scope, while others will function only when used in the correct type of scope. Note that some effects can change the current scope, or will execute their effects relative to the scope they were called from.

Effects are executed in order from the beginning of the effect block to the end. Effects are always the lvalue in a statement and can only ever use the `=` operator.

**Boolean form:**

Boolean effects use `yes` – or sometimes `no` – as the rvalue. These effects usually do not require any arguments, although some have optional arguments that can be invoked by using a block.

For example, this effect exiles an interest group leader:

```
# root = country
ig:ig_landowners = {
    leader = {
        exile_character = yes
    }
}
```

Boolean effects typically affect the scope in which the effect is executed. **Simple form:**

This style of effect requires a singular argument passed as the rvalue. These arguments can be things like:

| scope | `set_character_as_ruler = scope:foo` | `set_state_owner = c:FRA` |
|---|---|---|
| database key | `add_character_role = agitator` | `set_capital = STATE_EASTERN_THRACE` |
| value | `add_treasury = 5000` | `change_infamy = var:infamy_amount` |

Simple effects may affect the scope in which the affect is executed or the rvalue, depending on the effect.

**Complex form**

This style of effect uses several parameters in a script block. Some effects only accept this form even when having only a single argument.

```
# root = country
capital = {
    add_radicals_in_state = {
        culture = cu:french
        value = medium_radicals # this is a base game script value; equals 0.05
    }
}

# Kill Character has an optional "hidden" parameter
# For example, this will post a notification that the character has died
ruler = {
    kill_character = yes
}

# Adding the "hidden" parameter will silently kill the character
ruler = {
    kill_character = {
        hidden = yes
    }
}
```

Certain complex effects have an optional effect block with an implicit scope change included.

## Iterators

**Iterators** are used to run through a list of items and perform operations on them without having to specifically type out each item. Examples include characters in a country, states in a state region, or interest groups in a political party.

#### Trigger iterators

See
Trigger iterators
for documentation.
Trigger iterators take the form of `any_x` with the full name being indicative of what type of objects it iterates over. Like triggers, trigger iterators often require specific scopes to function.

```
# This trigger iterates all of the characters in a country
any_scope_character = {
    has_ideology = ideology:ideology_moderate
}

# This trigger iterates all countries globally
any_country = {
    is_in_geographic_region = geographic_region_europe
    country_has_primary_culture = cu:turkish
}
```

By default, trigger iterators return true if any single object fulfills the contained conditions. This can be changed by using the `count` or `percent` parameters. When using those parameters, the list of objects can be limited by using a `filter` trigger block, whose triggers are used only to determine which objects are tested against the main triggers.

#### Effect iterators

See
Effect iterators
for documentation.
Effect iterators come in three forms:

- `random_x` - This picks one random item from the list with the option to manipulate the weight of items
- `every_x` - This runs through all items in a list, in order
- `ordered_x` - This sorts the list by a provided value; it can then run through some to all of them or select a specific one by position in the list

Effect iterators can also accept an optional `limit` trigger block to exclude items in a list from consideration.

```
# This effect iterates all countries, but only those with enough money
every_country = {
    limit = {
        gold_reserves > 100000
    }
    add_modifier = modifier_has_money
}
```

## Control flow

See
Flow effects
for documentation of control flow effects.
PDXscript provides control flow in the form of conditional, `switch`, and `while` statements.

### Conditional Effect Statements

#### if Statements

These statements use a **limit** trigger block to control whether the contained effect is executed. For example:

```
if = { # Only exile unpopular characters
  limit = {
    popularity < 0
  }
  exile_character = yes
}
```

#### else_if / else Statements

If the trigger block returns false, the effect is not executed. Multiple conditional statements can be chained together by using **else_if** and **else** blocks. These are only evaluated if the immediately preceding **if** or **else_if** limit returned false. This can be used to branch your script execution. Your script will "return" to the point where you branched from once all script within the branch is finished. For example:

```
ruler = {
  # If this limit block is true, kill_character will be executed
  if = {
    limit = {
      culture != root.culture
    }
    kill_character = yes
  }
  # If the preceding limit block was false, exile_character will be executed
  else = {
    exile_character = yes
  }
}
# Regardless of the outcome of the conditionals above, your script will continue execution here
set_variable = yeeted_ruler
```

#### Nesting Conditional Statements

These statements can also be nested within each other for more complex branches. For example:

```
if = {
  limit = {
     # If this is true, the nested statements will be evaluated
    is_at_war = yes
  }
  if = {
    limit = {
       radical_fraction < 0.25
    }
    trigger_event = my_event.1
  }
  else = {
    trigger_event = my_event.2
  }
}
else = {
  trigger_event = my_event.3
}
```

### Conditional Trigger Statements

Triggers can also use conditionals with variants that prefix `trigger_` These follow the same logic as the effect statements, but are used to selectively activate triggers. For example:

```
AND = {
  gdp >= 5000000
  authority > 100
  # These statements will evaluate a different trigger based on the presence of the "declared_bankruptcy" modifier in scope
  trigger_if = {
    limit = {
      has_modifier = declared_bankruptcy
    }
    treasury > 0
  }
  trigger_else = {
    is_in_default = no
  }
}
```

### switch Statements

The `switch` statement allows for changing effect execution based on the returned value of a trigger.

Note that `switch` is limited to triggers which return a scope or value. This can also include using a variable, saved scope, or other event target directly.

```
# This evaluates the value of a variable "foo"
switch = {
  trigger = var:foo
  0 = { <effects> } # Executes if var:foo = 0
  1 = { <effects> } # Executes if var:foo = 1
  2 = { <effects> } # Executes if var:foo = 2
  fallback = { <effects> } # Executes if var:foo meets none of the prior criteria, optional
}
```

### while Statements

The `while` loop allows for the repetition of effects while certain conditions are true or for a given number of iterations.

If used with a `limit`, the enclosed effects repeat as long as the triggers in the `limit` remain true. For example:

```
while = {
  limit = { 
    treasury < 0 
  }
  add_treasury = 5000
}
```

If used with the `count` parameter, this behaves like a **for loop**, with the enclosed effects repeated for the specified number of iterations. For example:

```
while = {
  count = 100
  add_treasury = 5000
}
```

*Warning : When using while , you must be diligent to not put the game into an infinite loop. This will usually result in a game crash but can also hang the application or your machine.*

## Data management

PDXscript provides several methods of accessing, saving, and manipulating data.

### Variables

See the
Variable
page for more information about variables.
**Variables** are script-based event targets that can hold values or scopes. Variables do not need to defined or declared before they are assigned a value.

There are three types of variables: "regular," local, and global.

- "Regular" variables are saved to game objects and persist outside of the effect chain. These are accessed using the `var:` event target in that object's scope.

- Local variables are scope-agnostic and are cleared at the end of the effect chain. These are accessed using the `local_var:` event target in *any scope* until the end of the effect chain.
- Global variables are saved to the global state and persist out of the effect chain. These are accessed using the `global_var:` event target in any scope.

These are set and removed by effect. For example:

```
# This sets a variable in the current scope that is named "foo" and has a value of "1"
set_variable = {
  name = foo
  value = 1
}

# This removes a variable in the current scope with the name "foo"
remove_variable = foo
```

Triggers and effects are able to use variables as a target in the place of scripted objects or values. For example:

```
# This statement evaluates the value of the variable "foo"
if = {
  limit = {
    var:foo = 10
  }
  activate_law = law_type:law_autocracy
}

# This effect uses the value of the local variable "foo" as a multiplier value
add_modifier = {
  name = modifier_awesome_government
  multiplier = local_var:foo
}
```

### Saved scopes

See the
Scope
page for more information regarding scopes.
A saved scope is similar to a variable, except it only exists for the duration of an **effect chain** (called an event chain in the docs). Saving an object to a scope allows you to access that scope further downstream in your script.

Scopes are saved using the `save_scope_as` effect and accessed with the `scope:` event target. For example:

```
# This effect saves a country with poor relations and then triggers a diplomatic incident with them.
random_country = {
  limit = {
    relations:root < relations_threshold:neutral
  }
  save_scope_as = unfriendly_country
}
create_diplomatic_incident = {
  target = scope:unfriendly_country
  value = 10
}
```

Saved scopes are **forwarded to events and effects called from script**. Saved scopes persist until the end of the effect chain, at which point they are discarded. If an effect chain begins from an on_action, the game engine will sometimes forward scopes that are relevant to that on_action, such `scope:target` or `scope:recipient`

Only scopes that are available at the time the effect is called will be forwarded. For example:

```
ruler = {
  save_scope_as = ruler_scope # this scope will be forwarded to ruler_event.1
}
trigger_event = ruler_event.1
capital = {
  save_scope_as = capital_scope # this scope was saved after the trigger_event effect, and thus will not be forwarded to ruler_event.1
}
```

A saved scope can also be cached to a variable for access outside of its initial effect chain. For example:

```
# This saves the country scope FRA to a variable
c:FRA = {
  save_scope_as = france_scope
}
set_variable = {
  name = foo
  value = scope:france_scope
}

# In another script; since we saved the FRA scope to this variable, this the same as scoping via c:FRA
var:foo = {
  add_treasury = 5000
}
```

### Variable lists

See
Variable Lists
for more information on using variable lists.
Variable lists are used for storing objects in a list for later reference. Lists can be iterated and sorted, but you cannot directly scope any objects in a list with script alone.

### Variable maps

See
Variable Maps
for a detailed guide on using variable maps.
Variable maps are lists of key-value pairs, effectively functioning as arrays. These can be iterated and sorted as well.

### Script math

See
Script value
for a detailed guide on using script math.
PDXscript includes a robust math system which includes various arithmetic operations with support for conditional operations.

**Note**: A script value is calculated every time it is used. In cases where the value might be invoked frequently, such as in localization or a GUI, it is good practice to "cache" the value to a variable. This variable can be used comparisons with other script updating the variable only as needed. For example:

```
# initial effect that saved a script value to a variable
set_variable = {
	name = foo
	value = script_value_bar
}

# trigger elsewhere that checks the value of the variable
c:GBR.var:foo = script_value_boom

# this is more efficient than comparing the script value directly
c:GBR.script_value_var = script_value_boom
```

## Macros

Main article:
Macro
**Macros** are blocks of script that can be reused. There are two main types of macros: **scripted effects** and **scripted triggers**. The game evaluates macros as though they were defined directly in the script where they are used.

Scripted effects and triggers are defined in their respective folders: `/common/scripted_effects/` and `/common/scripted_triggers/`. They are invoked in script using their database key.

### Scripted triggers

```
# This is the definition in /common/scripted_triggers. It can be invoked using its key, "is_broke_trigger"
is_broke_trigger = {
	OR = {
		in_default = yes
		AND = {
			has_modifier = declared_bankruptcy
			gold_reserves < 0
		}
	}
}

# This is how it would appear in a trigger block:
if = {
    limit = {
        is_broke_trigger = yes
    }
    add_treasury = 100
}
```

### Scripted effects

```
# The base game defines this scripted effect:
the_balkan_league_activated_modifier_cleanser = {
	hidden_effect = {
		remove_modifier = balkan_wars_military_tech_boost_mod
		remove_modifier = balkan_wars_military_industry_overworked_mod
	}
}

# Which is called in the on_complete block of je_the_balkan_league
je_the_balkan_league = {
    <...>
    
    on_complete = {
        <...>
        the_balkan_league_activated_modifier_cleanser = yes
    }
}
```

### Parameters & substitution

Scripted triggers and effects can also define *parameters* that can be replaced when the macro is used.

These use `$$` to mark the parameters, for example:

```
# This trigger has two parameters "type" and "peril"
my_cool_trigger = {
	has_variable = $type$_expedition_peril_var
	var:$type$_expedition_peril_var >= $value$
}

# This can be invoked with its parameters like so:
my_cool_trigger = {
    type = antarctic
    value = 3
}

# Which the engine compiles into this script:
has_variable = antarctic_expedition_peril_var
var:antarctic_expedition_peril_var >= 3
```

Parameters are literal text replacement and so cannot be used to pass a saved value, such as a variable or saved scope's value.
