# 游戏桥接设计（Victoria 3 ↔ Agent）

> 状态：**设计提案**（未经本地验证，验证清单见文末）。验证通过的部分将升级为决策记录。
> 修订：2026-10-12 读写通道改为**消息队列/事件驱动**架构（作者提议，替代轮询拉取）。
> 前提约束（见《参考/游戏接入-victoria3》）：V3 无官方 runtime API；Paradox 脚本无运行时文件 IO；存档为 zip 文本。

## 1. 需求

| 能力 | 要求 | 延迟容忍 |
|------|------|---------|
| **读状态** | 列强关系、外交博弈、战争、排名等 → 写入日志 | **月度（游戏时间）推送 + agent 按需拉取**（MVP 定案） |
| **写动作** | 白名单外交操作，**仅两个**：创造外交博弈、加入外交博弈 | 分钟级真实时间 |
| **校验闭环** | 动作执行后确认真实生效，防"假成功" | 同步于读取周期 |

## 2. 架构：事件驱动的桥服务

```
┌──────────── Victoria 3 进程 ────────────┐
│ v3-bridge mod：on_action 输出 V3BRIDGE| 行 │
│ ⚠️ 游戏→外部的第一跳只能是文件             │
│    （Paradox 脚本无网络/IPC，无法直接入队） │
└───────────────┬────────────────────────┘
                │ game.log / 存档
                ▼
┌──────────── 桥服务（TS） ───────────────┐
│ ingest：tail/watcher 采集与解析           │
│   │ 解析出新行 → diff → 发布事件          │
│   ▼                                     │
│ EventBus（内存实现起步，接口可换 MQ）      │
│   ├ state.delta     细粒度外交事件        │
│   ├ state.snapshot  周期快照              │
│   └ action.receipt  动作回执              │
│                                         │
│ action 队列 ──▶ 串行注入消费者             │
│                    │ 注入后等状态事件      │
│                    ▼                     │
│                 校验器 ──发布 receipt ──┘ │
└───────┬─────────────────────────────────┘
        ▼
agent（pi 运行时）：POST /action 入队拿 task_id，
订阅事件流接收 state.delta / action.receipt；GET /state 查询当前值
```

对 agent 的接口：

```
POST /action  {type, ...}   → {task_id, status: queued}   // 入队即返回，异步
GET  /state                  → 当前快照（查询用；主要驱动力是订阅推送）
SUB  事件流（state.delta / state.snapshot / action.receipt）
```

agent 只见接口不见实现——内部通道（日志桥/存档、控制台/改档）与总线实现可随时替换，agent 代码零改动。

### 为什么是队列/事件而不是轮询

- **写通道：注入必须串行**。SendInput 序列不可并发（控制台只有一个、窗口焦点唯一），队列天然串行化并削峰——8 个 agent 同一外交回合同时行动也不会互相践踏（原"低频协调"方案的真实隐患）。
- **读通道：事件驱动更像真人**。agent 订阅"英俄结盟了"这类细粒度事件、有事即反应，而不是定时拉全量快照轮流读报；周期快照降级为背景校准。
- **回执异步化**：`/action` 入队即返回，结果由 `action.receipt` 事件送达——校验闭环（见 §6）自然融入同一事件流。
- **诚实的物理限制**：第一跳（游戏→文件）无法队列化，总延迟下限仍由 mod 的 on_action 输出频率决定；事件化优化的是第二跳延迟与并发正确性。要更低延迟需提高输出频率（性能上限待验证）。

## 3. 读取通道：月度日志快照（MVP 定案）

节奏定案：**每月（游戏时间）推送 + agent 按需拉取**——正好落在原生钩子 `on_monthly_pulse_country` 上，无需自建日级循环（日级留作远期优化）。

mod 侧（`v3-bridge` mod）：

- 挂 `on_monthly_pulse_country`（经官方追加机制：vanilla on_action 转调 modded on_action），对每个列强 country scope 输出**机器友好的一行式**：
  `V3BRIDGE|date=1836.4.1|tag=GBR|rank=1|prestige=...|relations:FRA=-20;...|plays:...|wars:...`
- 列强口径复用游戏原生的 `country_rank >= rank_value:great_power`（天然支持动态列强）
- 输出 effect：`debug_log`（存在性已确认；**变量插值签名待 script_docs**，S3）
- 落点：`Documents/Paradox Interactive/Victoria 3/logs/game.log`

桥服务侧：

- ingest tail 日志（文件占用与监听行为待验证 S5；不行则读取偏移轮询——**对文件是轮询，对 agent 仍是事件推送**）
- 每解析出新快照行：发布 `state.snapshot` 事件（月度推送）；agent 亦可 `GET /state` 随时拉取最新快照
- 远期优化：快照间 diff 出细粒度 `state.delta`（`PlayCreated`、`SideJoined`、`RankChanged`…），驱动事件式反应

### 兜底/校准：存档轮询 → 同一事件流

- 自动存档 watcher：解压（zip）+ 解析（Paradox 脚本 tokenizer，自写约 300 行）→ 走同一 diff→发布管线
- 用途：a) 日志桥失效时降级数据源；b) 周期性校准日志桥解析（防漂移）

## 4. 写入通道：动作队列

### 队列语义

- `POST /action` 校验白名单后入队，立即返回 `task_id`
- **单一串行消费者**逐条执行注入，天然互斥
- 每任务状态机：`queued → injecting → pending_confirm → confirmed | failed`；失败可配置自动重试（次数上限），多次失败进死信（供人工排查 + 发布 failed receipt）
- 队列实现：MVP 用内存队列 + 持久化日志（重启可恢复）；接口按 MQ 语义抽象，未来可换 BullMQ/Redis 而不动上层

### 主路径：控制台命令宏注入（白名单 = 两个动作）

前提：`-debug` 启动，控制台可用；`v3-bridge` mod 提供**游戏内宏**（原生宏系统，带参数）。

- **动作 → 宏映射（白名单即宏清单，agent 无法越权）**：

| 白名单动作 | 宏（草案） | 底层 effect（已在游戏文件确认） |
|-----------|-----------|-------------------------------|
| 创造外交博弈 | `bridge_create_play <initiator> <target>` | `create_diplomatic_play`（country scope；参数见 `history/diplomatic_plays/` 用例） |
| 加入外交博弈 | `bridge_join_play <tag> <side>` | `add_initiator_backers` / `add_target_backers`（需 play scope，进入语法待验证 S1） |

- **同一接口原则**：白名单动作必须映射到与玩家 UI 操作**同源的原生 effect**——agent 开博弈与玩家开博弈汇入同一个 DiplomaticPlay 系统（真博弈：AI 第三国照常评估站边、玩家收到通知、倒计时升级全套照走）。禁止 `annex`/`changeowner` 等直接改状态的旁路命令——它们绕过博弈流程，AI 无从参与、玩家不可见，威胁与承诺落不了地
- 宏定义在 `scripts/mod/v3-bridge/common/console_command_macros/00_bridge.txt`，参数细节待 script_docs 核实后启用
- **注入器已实现**：`scripts/s2-console-inject.ps1`（AttachThreadInput 强制前台 + SendInput 逐字符打字为默认模式，`-PasteMode` 剪贴板粘贴、`-UseScanCode` 兜底 raw input）——注入的文本只是 `宏名 参数`，极短极稳
  - ⚠️ 2026-10-12 实测结论：Claude Code 沙箱内合成键盘输入无法到达桌面应用（安全隔离，连自建靶窗口都收不到），**注入验证须在用户普通终端执行**（步骤见 `scripts/README.md` 阶段 A/B）
- **节律**：配合"外交回合"（暂停→结算→继续）或低频执行规避与玩家打架；队列保证回合内批量动作有序落盘

### 降级路径：存档改写 + 外交回合制

若控制台注入验证失败：暂停并保存 → 桥服务改写存档外交字段（博弈、关系、站队）→ 重载。改档动作同样走队列串行（与注入互斥，防混用）。体验变为外交回合制（brainstorm 候选玩法之一），技术完全可靠。待验证：普通模式存档无校验。

### 已否决

- **联机协议逆向**：工程量巨大、版本脆弱，否决
- **内存读写**：版本更新即失效，否决

## 5. EventBus 选型与边界

- **MVP：进程内内存 EventBus**（自写，topic publish/subscribe 语义，几百行）——单机单进程场景下 Redis/RabbitMQ/Kafka 均为杀鸡用牛刀
- **演进**：接口按标准 MQ 语义抽象；若 agent 多进程部署或需要跨机，换 BullMQ(Redis) 不动上层
- **与决策 0003 的边界**：0003 要求 agent **之间**的通信走飞书（信息不对称是玩法本体）。本总线只承载**游戏世界↔agent** 的感知与行动（agent"看世界"不是"听同事密谈"），不违反 0003。

## 6. 校验闭环（防假成功）

粘贴成功 ≠ 游戏执行成功。闭环依托同一事件流：

1. 消费者注入完成后任务置 `pending_confirm`
2. 校验器等待后续 `state.delta` 事件，确认目标状态变化（pact 出现/关系变动）
3. 匹配到 → 发布 `action.receipt(confirmed)`；超时 → 重试或 `failed`（附 error.log 抓取的失败原因）

## 8. 风险表

| 风险 | 影响 | 缓解 |
|------|------|------|
| 控制台注入不稳定 | 写入通道降级 | 回合制改档兜底，项目仍成立 |
| 日志 effect 不存在/不带变量 | 读取降级 | 存档 watcher（延迟变大） |
| on_action 频率低/日志量大 | 事件延迟高/解析压力大 | S7 实测；输出字段裁剪、采样 |
| V3 版本更新改 UI/脚本 | 注入器/解析器失效 | 桥服务接口不变，内部适配；版本锁定 |
| 与玩家输入打架 | 注入失败/误操作 | 外交回合节律 + 队列串行 + 校验闭环 |
| 存档改写被校验拦截 | 降级路径失效 | 先验证 S6 |
