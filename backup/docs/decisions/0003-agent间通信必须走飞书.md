# 决策 0003：agent 间通信必须走飞书，禁止进程内总线

- **日期**：2026-10-12
- **状态**：已采纳（作者拍板）

## 背景

早前调研的初判曾建议："agent 间消息用进程内总线/本地队列即可，不绕飞书一圈；飞书只是人类可见的界面层"——出发点是省 API 往返与延迟。作者否决此路线。

## 决策

**所有 agent 间通信必须通过飞书 API（bot 身份收发消息），不允许进程内直连总线或本地消息队列。**

## 理由

1. **信息不对称是外交游戏的本体**（与决策 0001 同源）：真实联机时你看不到别人在密谈什么，只能从后果推断。agent 互谈走飞书后，对玩家天然不可见——信息不对称由飞书的权限模型天然保证。进程内总线 + "选择性转播"等于自造一套可见性系统，且转播内容永远有"被篡改/被过滤"的嫌疑。
2. **飞书即审计日志**：全部外交过程（含 agent 之间）自动留痕于飞书会话，复盘、对局分析、直播回放都有完整可信的素材。
3. **单一通信事实源**：只有飞书一条消息路径，不存在第二套需要同步的状态。

## 后果

- 每国 agent 的全部收发都经飞书 API；8 国互谈的消息量上升后需关注飞书**频率限制（QPS）**，必要时做发送侧节流
- agent 间谈判延迟 = 飞书 API 往返，外交场景可接受
- MVP 范围不变（agent 互谈仍为 out-of-scope），本决策预先锁定其架构原则，避免日后推翻重写
- ⚠️ 待验证：飞书 **bot 与 bot 之间能否直接互发消息**。若平台不允许 bot-bot 私聊，则以"两国小群"形态实现双边密谈（agent 建群拉对方 bot），语义等价
  - 2026-10-12 更新：此问题已被**决策 0004** 化解——统一会话模型下一切会话皆为群，不依赖 bot-bot p2p

## 被否决的方案

- **进程内总线 / 本地消息队列直连**：破坏信息不对称的天然性；产生第二套消息状态；转播机制有篡改嫌疑
