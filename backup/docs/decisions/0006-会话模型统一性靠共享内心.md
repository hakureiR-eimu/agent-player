# 决策 0006：会话模型——agent 统一性靠共享内心，会话 = 窗口

- **日期**：2026-10-13
- **状态**：已采纳（作者提出方向，讨论后拍板）

## 背景

决策 0002 定了基底（Claude Agent SDK）后，会话粒度悬而未决：一国 agent 是所有通道共用一条对话流（一国一会话），还是每个飞书会话各开一个（多会话）？多会话之下，agent 的人格与认知统一性靠什么维持？

## 决策

**每国 agent = 共享内心 + 会话集：**

- **共享内心**：薄层（规则五件，0005）+ 一个沙箱（`thin/` `world/` `self/` `memory/`）——人格、盘算、记忆全在文件里，该国所有会话共读共写同一套
- **窗口会话 ×N**：每个飞书会话（公屏、双边群、集团群，0004）对应一个，transcript 只含该窗口对话；system prompt = 薄层 + 窗口头（百来字）；只收聊天消息——被动响应的宿主
- **内心会话 ×1**：无聊天对象；收月度快照通知与动作回执；盘算（readiness / 阶段 / 目标编辑）与主动行为的发起地
- **不设操作会话**：游戏动作是工具调用，注册给所有会话——窗口里谈崩当场开博弈，正是"谈判落地"（mvp 验收）的形态
- **会话不常驻**：事件到达 → resume 该会话 transcript → 跑一轮 → 子进程退出；**国级串行**——一国同时至多一个 turn（不分窗口），保护共享沙箱里 `self/` 的写
- **快照通知式注入**：全量落 `world/` 文件，事件体只是短通知（就位 + 较上月要点）

## 理由

1. **与真人同构**：真人多窗口一个脑子——窗口里只有窗口的对话，脑子里装人格与账；agent 的"脑子" = 薄层 + 共享沙箱文件
2. **上下文干净**：一国一会话把全部通道混进一条流——长对局 transcript 膨胀快、compaction 集中且丢细节、注意力被无关会话稀释；多会话按窗口分压
3. **transcript 语义清晰**：transcript = 聊天记录（窗口）/ 内心独白（内心），与飞书侧"一切皆会话"（0004）一一对应，而非把 N 个会话压进 1 条流
4. **生产级同构（OpenClaw）**：session key = `agent:<agentId>:<peer-suffix>`——同一 agent 面对不同对话对象开不同 session，统一性靠 agent 级 workspace 与跨会话记忆；LangBot 同样按会话并发控制。一国一会话反而是研究型框架的单房间模型（pi-groupchat）

## 后果

- 宿主维护**会话映射表**（飞书会话 ↔ SDK session id）；窗口随拉群按需登记
- 进程模型变为按需 resume：活跃子进程 = 活跃 turn（≤8 量级），资源压力骤降；代价是每事件 resume 的上下文重建，靠 prompt cache 缓解——**成本待实测**（挂主体程序需求 待定问题）
- 国级串行比 OpenClaw 的 per-session 并发更严——必须如此，因为各窗口共享可写的 `self/`
- 跨窗口记忆文件化：宿主机械落 `memory/chats/` 只读记录（"翻聊天记录"能力）+ agent 自记摘录——一致性从"上下文里恰好有"变成"翻记录 + 记重点"，与真人记忆方式一致
- 故障面更小：崩溃只丢一个未完成 turn，resume 即恢复
- 开局触发移入内心会话（开局盘算本就是内心会话职责）

## 被否决的方案

- **一国一会话**（原设计）：上下文混流、compaction 集中丢细节、transcript 语义含混（见理由 2 / 3）
- **两三会话缩减版**（聊天 1 + 游戏 1，或聊天 1 + 游戏 1 + 操作 1）：三通道混流痛点原样保留，而窗口路由复杂度几乎不变——真正该砍的是操作会话（已砍，动作是工具随处可用）
