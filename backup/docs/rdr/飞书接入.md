# 飞书接入：网关、凭据与消息流

> 定位：本文定义**宿主的飞书侧**——怎么接入（8 应用长连接网关）、凭据怎么管（一国一应用、闭包绑定）、消息怎么流（收消息双路：玩家消息按群成员路由、agent 消息发送侧扇入）、对外发送（节流与载体选型）。飞书网关是宿主四件之一（宿主形态见 `docs/rdr/主体程序需求.md` §一），本文展开其内部。
> 分工：agent 怎么在飞书里调用工具聊天——`send_message`（公屏）/ `dm`（私聊）的工具语义、会话解析、发言限流——归**沟通文档（待建）**；工具面只有这两个，且**工具名与描述不含"群"等实现词**（agent 认知里没有群，找或建 2 人群归宿主 execute 内，0004 修订）；工具注册机制（内存 MCP server、闭包怎么构造）归 `主体程序需求.md` §5.2，本文只讲绑定进去的是什么（凭据、可见性）。工具的语义声明在 `agent需求.md` §2.1。
> 依据：决策 0001（飞书一国一应用）、0003（agent 间通信必须走飞书——唯一信道）、0004（一切皆群派生、成员制可见性）；平台行为先例见 `参考/相关项目-多agent聊天基座.md`（2026-10-13，13 项）。
> 修订：2026-10-13 拆分自「主体程序和多agent需求」（该文更名 `主体程序需求.md`，聚焦宿主与生命周期）：长连接定案论证、平台限制情报（bot 互听）、收消息双路、发送载体选型及其待定问题移入本文，定案全部保留。同日先例调研修订（证据：`参考/相关项目-多agent聊天基座.md`，OpenClaw / telegram-agent-mcp / CloseCrab / telegram-presence / sotopia 等 13 项）：**收消息定案双路**——玩家消息走长连接推送按群成员路由，agent 消息走宿主发送侧扇入（Telegram 实证、飞书高置信线索：bot 之间互不投递消息，"群内 agent 互相看见"不能依赖平台推送）；WS 长连接与"宿主统一收发"获多源佐证；长连接实测清单扩充 bot 互听行为。

## 一、总览：飞书在架构里的位置

- **玩家 ↔ 飞书 ↔ 宿主**：玩家经飞书（8 国应用，一国一应用）与宿主双向收发；两通道（公屏 / 私聊）统一为群会话实现（决策 0004，2026-10-13 修订：拉群移除）
- **飞书网关**（宿主四件之一）职责三件：8 应用事件接入（长连接，§二）→ 国别路由（§四）→ 发送节流（§五）；**兼管发送侧扇入**（§四）
- **部署前提**：宿主必然本地部署（桥的 SendInput 注入必须与游戏进程同机）——这是接入方式选型的出发点（§二）

## 二、接入方式：长连接（定案 2026-10-12）

**长连接（`WSClient`）**——8 应用各建一条 WebSocket，由本地宿主**主动连出**，NAT 后无碍，纯本地闭环。选择依据：宿主本地部署（MVP 无桥后是选择：个人机器运行、凭据本地保管；未来接桥后成为必然——桥的 SendInput 注入必须与游戏进程同机），webhook 要求公网端点（云主机/内网穿透/公网 IP 转发）属纯多余基建。未来若公网化部署，事件接入层做薄抽象即可切换 webhook，路由与队列不动。

**先例佐证（调研 2026-10-13）**：LangBot（飞书适配 WS 长连接为默认、多 bot 实例并存已验证）与 OpenClaw（飞书插件默认 WebSocket，单网关多 appId 配置官方支持）双双印证此选型。

## 三、凭据与配置：一国一应用（0001）

- 8 国飞书应用凭据与 应用 ↔ 国家 TAG 对照入宿主配置（启动加载见 `主体程序需求.md` §四）；开局前 8 应用已建（脚本自动化，0001）
- **凭据只存在于宿主配置与工具闭包，agent 参数里永远只有会话名与文本**——隔离模型第 3 层（`主体程序需求.md` §二）："以普鲁士身份发言"在工具层无此能力
- 发消息工具闭包绑定该国 app token：注册机制（内存 MCP server + execute 闭包）见 `主体程序需求.md` §5.2，工具语义细则归沟通文档（待建）
- 会话可见性（隔离第 4 层）：本国只能进入自己发起或被拉入的会话——私聊目标取自薄层名录（0004 修订后工具面只暴露公屏与私聊），他国私聊对本国工具层**不存在**——判定依据是 0004 的成员制，实现落点在飞书工具的 execute 内

## 四、平台限制情报与收消息双路（定案 2026-10-13）

**平台限制情报（调研 2026-10-13，收消息双路的依据）**：**bot 之间互不投递消息**——telegram-agent-mcp 在 Telegram 上实证（Bot API 不把一个 bot 发的消息投给另一个 bot 的 getUpdates，@mention / 隐私模式 / 双 admin 均绕不过，bot-bot DM 直接被拒）；OpenClaw 生产文档称飞书同样默认忽略其他 bot 的消息，即使配 `im:message.group_at_msg.include_bot:readonly` 等权限也**只在被 @ 时才投递**，且 bot 间不能互发私聊；另有独立佐证（2026-10-13 补查）：feishu-bot-relay 中转项目的立项依据即"bot A 在群内 @ bot B，B 收不到任何消息事件"（有人专门造轮子绕过，是最强的行为证据）、V2EX 社区讨论同；官方文档的消息事件模型仅面向"用户→机器人"方向，**无 bot↔bot 支持的明文**——结论定为"多源印证的行为限制、待本地实测"，不称"平台事实"。推论：**"群内 agent 互相看见对方发言"不能依赖飞书推送**，必须由宿主在发送侧扇入（见下）——这同时是 telegram-agent-mcp（发送侧写总线）与 OpenClaw broadcast（协调者扇出）的同解法。

**收消息不是工具，且分两路**：

- **玩家消息（真人所发）**：飞书长连接推送 → 宿主按"消息所在群的成员 bot"路由，成员国各收一份，注入其对应**窗口会话**（会话模型见 agent需求 §1.4、决策 0006）
- **agent 消息（接入国所发）**：**发送侧扇入**——agent 发言本来就必须经宿主的 send_message 工具出站（凭据闭包，§三），发送成功后宿主直接把该消息作为事件注入群内**其他成员国**的对应窗口会话，不依赖飞书向其他 bot 投递（依据见上平台限制情报）。消息本身以飞书消息形态真实存在于群里（玩家全程可见、可回放），不违反决策 0003——飞书仍是唯一信道，玩家侧的呈现与投递归飞书，agent 侧的送达归宿主；对 agent 而言它只是"在群里看到有人说话"，来源感知无差别（与眼中皆玩家定案相容）。扇入范围＝群成员中除发送国外的接入国；双边群（玩家×一国）无扇入对象，天然退化为单播

agent 没有"收"这个动作，只有"被触发"（对应 agent需求 §1.6 的行为循环）。两路消息汇入宿主的同一事件队列、同一触发格式（队列与触发注入见 `主体程序需求.md` §六），下游无差别。

bot 互听行为待本地实测确认（见待定问题），但架构不依赖实测结果：无论飞书行为如何，agent 消息统一走扇入这一条路径（若平台也能投递则事件订阅面收窄，避免双径去重）。

## 五、发送侧：节流与载体

**发送节流**：对外发送做节流（网关职责之一）。

**接入载体（待定，调研 2026-10-13）**：收与发分开看——

- **收消息（飞书 → 宿主）**：维持长连接定案，载体为官方 Node SDK（`@larksuiteoapi/node-sdk`，含 `WSClient`）。CLI 是"调用一次、返回一次"的工具，只能主动去查，接不住飞书推过来的消息
- **发消息（宿主 → 飞书：发言 / 建群 / 拉人）**：出现新候选**官方 lark-cli**（`github.com/larksuite/cli`，2026-03 开源，larksuite 团队官方维护，npm `@larksuite/cli`，Agent 原生设计——结构化输出、注入防护、200+ 命令，Messenger 域覆盖收发 / 建群 / 查历史），并提供面向"嵌入自己 Agent"的企业扩展路径（集中凭据、统一审计、受限命令面）；同源另有官方 MCP（`@larksuiteoapi/lark-mcp`）。候选用法：宿主工具 execute 内转调（agent 不直接接触 CLI——工具面白名单与凭据隔离不因此放开），以及运维 / 调试侧人工使用。待验证项见待定问题

## 六、开局与关停的飞书侧

- **开局就位**（初始化流程步骤 2，序列见 `主体程序需求.md` §5.3）：8 应用已建（脚本自动化，0001）；凭据入宿主配置；创建全员公屏群 + 预建"玩家×每国"私聊（2 人群，0004 修订）——会话模型与命名细则归沟通文档（待建）
- **关停**：断开 8 条长连接（关停序列见 `主体程序需求.md` §七）

## 验收标准（飞书侧）

- 8 条长连接建立，飞书事件按国别路由到正确国家；桥事件汇入同一队列（队列侧验收见 `主体程序需求.md`）
- agent 群内发言经发送侧扇入送达群内其他成员国（不依赖 bot 间投递），玩家消息与扇入消息在触发格式上无差别
- 信息隔离：他国私聊不出现在本国 transcript 与 `world/` 投影中（引 mvp 验收；三通道收发细则归沟通文档，待建）
