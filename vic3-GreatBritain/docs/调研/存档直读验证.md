# 维多利亚3 存档直读验证（2026-11-18）

## 1. 结论

**不适合让 agent 直接读存档来获取游戏状态。** 不是 agent 解析能力不够——存档的物理结构（zip 包）和二进制编码（token 流）都能解析，本会话已实际写出解析器读出了内容。不可行的原因只有一个，但足够致命：

- 存档里所有字段名（key）都是 16 位 token 编号，还原成可读名字需要一张「编号 → 名字」的对照表（下称词表）。**词表是 Paradox 私有资产，没有公开来源**（排查过程见 §4），社区最全的 pdx.tools 也闭源持有。
- 自己逆向词表等于把产品建在对私有格式的逆向上：游戏版本一更新、一加 mod，词表就可能变，每次都要重做，脆且不可控。

注意结论的边界：**被否决的只是「直读二进制存档」这一条路**。游戏目录里的静态内容（`common/` 下的建筑、科技、法令定义等）本来就是明文脚本，agent 直接读没有任何障碍；动态局内状态的获取走 mod 导出（已定方案，见 `vic3-GreatBritain/docs/prd/游戏接入.md`）。

这个验证的动机是「给 agent 一个数据库让它自己写 SQL」的接口形态问题：验证对象是存档能否当 agent 的直接数据源。答案是不能——存档要变成可读数据，中间必须有一个固定的转档器（mod 导出日志、文本存档、或第三方转文本工具），agent 只能消费转档之后的产物。

## 2. 存档的物理结构（实测）

验证样本：`C:\Users\ZhangJunWei\Documents\Paradox Interactive\Victoria 3\save games\大清_1839_06_22.v3`（15MB，1839 年的大清局），以下均为本机实测。

| 层 | 事实 |
|---|---|
| 文件头 | `SAV` + 一串版本哈希的文本行（如 `SAV0105372ddb8f...`）+ 换行，共约 19 字节，之后直接是 `PK` |
| 容器 | 标准 zip，无需处理前缀即可用任何 zip 库解开 |
| 条目 1 | `meta`，解压后 1.4KB——存档元数据（版本、国名、日期） |
| 条目 2 | `gamestate`，解压后 110MB——全部游戏状态 |

这一层没有任何障碍。目录下共 17 个存档（5 个国家的局），结构一致。

## 3. gamestate 的二进制格式（实测，已跑通）

gamestate 是 Paradox 的 Jomini 序列化二进制格式。结构本身不复杂，一个下午的探索已解析出有意义的内容：

**编码规则**（token 值定义抄自开源库 jomini 的 `lexer.rs`，源码原文已核）：

| token | 含义 | 载荷 |
|---|---|---|
| 0x0001 | `=` | 无 |
| 0x0003 | `{` | 无 |
| 0x0004 | `}` | 无 |
| 0x000c | i32 | 4 字节 |
| 0x000d | f32 | 4 字节 |
| 0x000e | bool | 1 字节 |
| 0x000f | 带引号字符串 | u16 长度 + 内容（UTF-8） |
| 0x0014 | u32 | 4 字节 |
| 0x0017 | 不带引号字符串 | u16 长度 + 内容 |
| 0x0167 | f64 | 8 字节 |
| 0x0243 | RGB | 6 字节 |
| 0x029c / 0x0317 | u64 / i64 | 8 字节 |
| 其余数值 | **字段名（key）的词表编号** | 无——这就是需要词表的部分 |

**已读出的内容**（值全是明文内联，所以能读）：游戏版本 `1.13.11`、玩家国名「大清」、国家等级 `unrecognized_major_power`、地图配色（`ce_dragon_china.dds` 等）、全部规则设置（`achievements_allowed`、AI 侵略性等）、启用的 DLC 列表、玩家名、对局 GUID。

**未解完的格式细节**：数字 key 的编码（`0x0003`+u16 疑似）等还有少量模式没确认——即使不考虑词表，格式逆向本身也还有长尾，这从侧面印证「自己维护解析器」的成本判断。

## 4. 词表获取途径逐条排查（全部堵死）

| 途径 | 结果 |
|---|---|
| 游戏安装目录（`Victoria 3/` 全盘 find） | 没有 token 文件；游戏运行时从脚本现建词表，不落盘 |
| 开源库 jomini（rakaly 组织） | 只有 token 类型定义（§3 那张表），不含任何游戏的词表 |
| librakaly（pdx.tools 的 C 接口库） | 代码引用 `assets/tokens/vic3.txt`，但该文件被 gitignore，构建脚本只写空占位 |
| vic3save crate（词表的真正出处） | GitHub 上不存在、crates.io 上不存在——pdx.tools 闭源持有 |
| 第三方项目 Vic3SaveAnalyzer | 分发编译好的 `rakaly.dll`（词表编进了二进制里）——能用，但等于依赖闭源资产的黑盒，不可控 |

CK3、EU4 等游戏的词表同样情况（社区靠游戏版本发布后重新生成），Vic3 连社区公开版都没有。

## 5. 对已定方案的关系

本次验证不改变任何已定方案，反而印证了 prd（`vic3-GreatBritain/docs/prd/游戏接入.md`）的两条既有设计：

1. **mod 月度导出到 game.log** 是读动态状态的主路线——绕开存档格式，游戏自己把状态写成明文。
2. **debug_mode 下 pdx_settings.json 可设文本存档** 做全量校准——同样是让游戏自己产出明文，只是粒度是整局。

补充一条兜底：如果将来需要读任意历史存档（非 debug 局），现成工具 rakaly（pdx.tools）能把 .v3 一步转成明文文本，但依赖它的闭源 dll，只作为应急手段记录在案，不进主路径。
